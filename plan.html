01 — Overview

Find House Architecture

A broker productivity platform: React frontend + Supabase backend, built with a clean service layer so migrating to a standalone backend later requires zero component changes.

Core Principles

🔌
Migration-Ready
Components never import Supabase directly. All data access is through the service layer.
📦
Modular
Each domain is a self-contained module with its own types, services, hooks, and UI.
🔒
Single Responsibility
Business logic lives in services. Components only handle rendering and user interaction.
🗂️
Session-Isolated
Property submissions are strictly isolated by session ID, never by message history scanning.
💡 The WhatsApp intake runs via Supabase Edge Functions (serverless) today. When we migrate, these Edge Functions become a standalone Express/Fastify server — the service layer contracts stay identical, only the transport changes.

04 — Authentication

Broker & Admin Login

Both brokers and admins authenticate through Supabase Auth (email + password). The role is encoded in the JWT as a custom claim. The same login page reads the claim and redirects accordingly.

Two Roles, One Auth System

PropertyBrokerAdmin
Login URL/login/login (same page)
Redirect after login/dashboard/admin
Role claimapp_metadata.role = "broker"app_metadata.role = "admin"
Account creationSelf-registration via sign-up formManual — SQL or Supabase dashboard only
Broker profile requiredYes — row must exist in brokers tableNo broker profile
RLS accessOwn properties and sessions onlyService role key via Edge Functions
💡 app_metadata is set server-side only and is included in the JWT automatically. The React app reads session.user.app_metadata.role — it cannot be forged by the user. Brokers who try to access /admin are redirected away by the <AdminRoute> guard.

Login Flow

1
User submits email + password at /login
Single login page for both roles. No separate admin URL needed — the role determines where they go.
2
Supabase Auth validates credentials, returns JWT
JWT payload includes app_metadata.role. Stored in Supabase's own session (localStorage). Automatically refreshed.
3
Auth store reads the role claim
session.user.app_metadata.role === 'admin' → redirect to /admin. Otherwise → redirect to /dashboard. If no broker record exists yet, redirect to /onboarding to complete profile.
4
Route guards enforce access on every navigation
<BrokerRoute> requires a valid session + broker role. <AdminRoute> requires admin role. A logged-in broker visiting /admin is bounced to /dashboard.

Route Guard Implementation

TypeScript modules/auth/guards.tsx 
// BrokerRoute — requires authenticated broker
export function BrokerRoute({ children }: { children: ReactNode }) {
  const { session, role, isLoading } = useAuth();
  if (isLoading) return <PageSpinner />;
  if (!session) return <Navigate to="/login" replace />;
  if (role !== 'broker') return <Navigate to="/admin" replace />;
  return <>{children}</>;
}

// AdminRoute — requires admin role
export function AdminRoute({ children }: { children: ReactNode }) {
  const { session, role, isLoading } = useAuth();
  if (isLoading) return <PageSpinner />;
  if (!session) return <Navigate to="/login" replace />;
  if (role !== 'admin') return <Navigate to="/dashboard" replace />;
  return <>{children}</>;
}

// Usage in router.tsx
<Route path="/dashboard/*" element={
  <BrokerRoute><DashboardLayout /></BrokerRoute>
} />
<Route path="/admin/*" element={
  <AdminRoute><AdminLayout /></AdminRoute>
} />

Creating the First Admin Account

Admin accounts are never created through the sign-up form. Create them manually in two steps:

Step 1 — Create the user in Supabase Auth

SQLSupabase SQL Editor or psql
-- Option A: Supabase dashboard → Authentication → Users → "Add user"
-- Then run Step 2 below to set the role.

-- Option B: Using the Supabase service role key via API
-- POST https://<project>.supabase.co/auth/v1/admin/users
-- Body: { "email": "admin@findhouse.app", "password": "...", "email_confirm": true }

Step 2 — Set the admin role claim

SQLRun in Supabase SQL Editor
-- Replace the UUID with the user's actual ID from auth.users
UPDATE auth.users
SET raw_app_meta_data = raw_app_meta_data || '{"role": "admin"}'::jsonb
WHERE email = 'admin@findhouse.app';

-- Verify
SELECT id, email, raw_app_meta_data
FROM auth.users
WHERE email = 'admin@findhouse.app';
⚠️ The role claim is in raw_app_meta_data (server-side). Do not set it in raw_user_meta_data — that is user-editable and would be a security hole. Supabase exposes app_metadata in the JWT as read-only to the client.

Broker Registration Flow

TypeScriptmodules/auth/AuthService.ts
// Registration creates two records atomically
async function registerBroker(email: string, password: string, fullName: string) {
  // 1. Create Supabase Auth user (role defaults to "broker" via a DB trigger)
  const { data, error } = await supabase.auth.signUp({ email, password });
  if (error) throw new AuthError(error.message);

  // 2. Create broker profile (trigger handles this automatically — see below)
  // The trigger fires on INSERT into auth.users and creates the brokers row.
  return data.user;
}

Database trigger — auto-create broker profile on signup

SQLsupabase/migrations/001_brokers.sql
CREATE OR REPLACE FUNCTION handle_new_broker()
RETURNS TRIGGER AS $$
BEGIN
  -- Only create broker profile if role is not 'admin'
  IF (NEW.raw_app_meta_data->>'role') IS DISTINCT FROM 'admin' THEN
    INSERT INTO public.brokers (id, email, full_name)
    VALUES (
      NEW.id,
      NEW.email,
      COALESCE(NEW.raw_user_meta_data->>'full_name', '')
    );

    -- Set the broker role claim
    UPDATE auth.users
    SET raw_app_meta_data = raw_app_meta_data || '{"role": "broker"}'::jsonb
    WHERE id = NEW.id;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE TRIGGER on_auth_user_created
  AFTER INSERT ON auth.users
  FOR EACH ROW EXECUTE FUNCTION handle_new_broker();

07 — Service Layer

The Migration-Ready Pattern

This is the core architectural decision. Every module defines a TypeScript interface for its service. The current implementation uses Supabase. The future implementation uses REST. Components and hooks never change.

🔌 The rule: Components import hooks. Hooks import the service. The service imports lib/supabase.ts. Nothing else imports from lib/supabase.ts. To migrate: write a new service implementation, update the factory in lib/services.ts, done.
TypeScript modules/properties/PropertyService.ts 
// Step 1: Define the interface (never changes)
export interface IPropertyService {
  getProperties(brokerId: string): Promise<Property[]>;
  getProperty(id: string): Promise<Property | null>;
  getPropertyBySlug(slug: string): Promise<Property | null>;
  createProperty(data: CreatePropertyInput): Promise<Property>;
  updateProperty(id: string, data: UpdatePropertyInput): Promise<Property>;
  deleteProperty(id: string): Promise<void>;
  updateStatus(id: string, status: PropertyStatus): Promise<Property>;
}

// Step 2: Supabase implementation (today)
export class SupabasePropertyService implements IPropertyService {
  constructor(private client: SupabaseClient) {}

  async getProperties(brokerId: string): Promise<Property[]> {
    const { data, error } = await this.client
      .from('properties')
      .select('*, property_media(*)')
      .eq('broker_id', brokerId)
      .order('created_at', { ascending: false });
    if (error) throw new ServiceError(error.message);
    return data.map(toProperty);
  }
  // ... rest of implementation
}

// Step 3: Factory — the ONLY migration touch point
export function createPropertyService(): IPropertyService {
  return new SupabasePropertyService(supabaseClient);
  // Migration: return new RestPropertyService(API_BASE_URL);
}
TypeScript modules/properties/useProperties.ts

08 — WhatsApp Flow

Submission Lifecycle

The complete journey from a broker's WhatsApp message to a published property website. Each step maps to a specific function and database state change.

Message Processing Flow

1
Webhook Receives Message
Meta sends POST to /functions/v1/whatsapp-webhook. Verify HMAC-SHA256 signature. Acknowledge with 200 immediately (Meta requires <20s response). Process async.
2
Authorize the Number
Look up the sender's phone number in whatsapp_numbers. If not found or is_active = false, silently drop — no response, no error. Log the attempt.
3
Deduplicate
Check session_messages.wa_message_id. If already exists, the webhook fired twice — skip. This handles Meta's at-least-once delivery guarantee.
4
Classify the Message
Determine type: GREETING (Hi, Hello, etc.) → no action. DONE → finalize session. PROPERTY_INFO → proceed. OTHER → ignore. Classification uses simple string matching for DONE and GREETING; treats everything else as PROPERTY_INFO.
5
Session Routing
Find the broker's current COLLECTING session. If none exists → create a new session (status: COLLECTING). If one exists → add message to it. A broker can never have two COLLECTING sessions simultaneously (enforced by unique partial index).
6
Store Message + Media
Insert row into session_messages with the session_id. For image/video: download media from WhatsApp CDN using the media ID, upload to Supabase Storage at submissions/{session_id}/{wa_message_id}, store the path.
7
DONE Received — Finalize Session
Update session status to PROCESSING. Set done_received_at. No more messages will be added to this session (new property messages will create a new session). Invoke process-submission Edge Function asynchronously.
8
AI Extraction
Fetch all session_messages WHERE session_id = ? only. Build a structured prompt with all text + image URLs. Call Claude API. Parse the structured property JSON response. Never invent data — missing fields stay null.
9
Create Property + Media Records
Insert into properties with the extracted data and the session's broker_id. Generate a unique slug. Insert property_media rows for each media file, with AI-assigned categories. Link submission_sessions.property_id.
10
Session Completed → Send WhatsApp Notification
Update session status to COMPLETED. Invoke send-notification Edge Function with the property URL: https://findhouse.app/p/{slug}. Send the URL back to the exact WhatsApp number that submitted.

Failure Handling

Failure PointActionState
Media download failsRetry 3x, then skip that media item. Continue processing.Session continues
AI extraction failsSet session status FAILED, store error in failure_reason. Preserve all messages.FAILED — retryable
Property creation failsSet FAILED. Nothing partial is committed (transaction).FAILED — retryable
Notification failsProperty already created. Log failure. Broker sees it in dashboard. Retry notification separately.COMPLETED (property exists)
DONE without property infoDetect no PROPERTY_INFO messages in session. Set FAILED with reason. No property created.FAILED
09 — Migration Path

Supabase → Standalone Backend

The entire migration is designed to happen without touching a single React component. The service layer is the only boundary that changes.

What Changes

LayerToday (Supabase)After MigrationChanges?
Components Call hooks Call same hooks None
Hooks Call service functions Call same service interface None
Service interfaces TypeScript interfaces Same interfaces None
Service implementations SupabaseXxxService RestXxxService Rewrite (new file)
Service factory new SupabasePropertyService() new RestPropertyService(API_URL) One line per service
Auth Supabase Auth JWT Backend-issued JWT AuthService rewrite
Edge Functions Deno serverless Express/Fastify routes Port logic (same business logic)
Database Supabase Postgres Any Postgres Migrations portable
File storage Supabase Storage S3 / R2 / similar StorageService rewrite

Migration Steps (When the Time Comes)

A
Set up standalone server (Node.js)
Create Express/Fastify app. Port the Edge Functions to route handlers. Same business logic, same database schema.
B
Write REST service implementations
Create RestPropertyService, RestAuthService, etc. implementing the same TypeScript interfaces. Each calls fetch(API_BASE_URL + ...).
C
Update service factories
In lib/services.ts, change one line per service. Gate it behind an env var to run both in parallel for testing.
D
Migrate data and storage
pg_dump from Supabase Postgres. Migrate media files from Supabase Storage to the new provider. All URLs are stored as paths, not full URLs — update the storage base URL in config.
